Live Auction Platform – System Design & Stack Proposal

Campaign-based online auctions with real-time bidding, anti-sniping time extension, outbid notifications and a winners board. Sized for 50–100 concurrent bidders, optimised for fast implementation. Prices in VND (default) or USD; UI in Vietnamese (default) or English; username/password login now, SSO later.

Key design decisions

  • Bids are written via REST, state is pushed via WebSocket. Writes get proper HTTP errors, rate limits and idempotency keys.
  • One row lock per auction (SELECT … FOR UPDATE) serialises every bid. Two users submitting the same price at the same time: first wins, second gets a clear "outbid" error.
  • Server clock is the only clock. Clients render a countdown from a server-time offset.
  • Anti-sniping: a bid inside the last extend_window seconds pushes current_end_at to now + extend_by.
  • Outbid alerts target the previous leader's private socket room, play a sound and raise a browser Notification.
  • Winners board is materialised into auction_results at auction end and ordered by final_price − start_price.
Why this stack: one language (TypeScript) end-to-end, shared types between API and UI, Socket.IO handles reconnection/rooms out of the box, and PostgreSQL row locks give correct concurrency without building a custom matching engine. Everything runs on a single server for this load.

3. Currency, language & authentication

Currency – VND default, USD optional

  • Per campaign. campaigns.currency is 'VND' (default) or 'USD'; every auction in the campaign inherits it and every socket payload / API response carries it so the UI never guesses.
  • Storage. One NUMERIC(14,2) column for both. VND has no minor units, so the API rejects non-integer VND amounts; USD allows cents. Suggested defaults: VND step 50.000 ₫, USD step $5.
  • Formatting is done on the client with Intl.NumberFormat, driven by the UI locale and the campaign currency, never hard-coded:
export function formatMoney(amount: string | number, currency: 'VND' | 'USD', locale: 'vi' | 'en') {
  const tag = locale === 'vi' ? 'vi-VN' : 'en-US';
  return new Intl.NumberFormat(tag, {
    style: 'currency', currency,
    maximumFractionDigits: currency === 'VND' ? 0 : 2,
  }).format(Number(amount));
}
// formatMoney(1200000, 'VND', 'vi') → "1.200.000 ₫"
// formatMoney(1200000, 'VND', 'en') → "₫1,200,000"
// formatMoney(1250.5,  'USD', 'en') → "$1,250.50"
  • Bid input is a locale-aware numeric field (thousand separators while typing, parsed back to a plain number before submit). Quick-bid buttons show the formatted absolute amount, not just “+1 step”.
  • No conversion. A campaign is priced in exactly one currency; the winners board and exports use that currency. Mixed-currency reporting (if ever needed) is an admin-only concern.

Language – Vietnamese default, English optional

  • UI strings: next-intl with locale-prefixed routes (/vi/… default, /en/…). Message catalogues in messages/vi.json and messages/en.json; the shared package exports the same keys for server-side messages (notification titles, error codes).
  • Locale resolution: URL prefix → users.locale (if logged in) → NEXT_LOCALE cookie → Accept-Language → vi. A header switcher writes the cookie and PATCH /auth/me.
  • Content: product/campaign name and description are JSONB { vi, en }; the admin form shows both tabs, English optional, with fallback to Vietnamese at read time. Images and prices are language-independent.
  • Server-sent text: socket events and API errors carry a code plus parameters (e.g. { code: 'BID_TOO_LOW', minAllowed }); the client renders the sentence in the active language. Browser notifications are rendered client-side for the same reason.
  • Dates/times: stored UTC, displayed in Asia/Ho_Chi_Minh by default via Intl.DateTimeFormat (24-hour in vi, 12-hour in en). Countdown labels (“còn 00:29” / “29 s left”) come from the catalogue.

  readonly name: 'local' | 'oidc' | 'saml';
  authenticate(input: LoginInput): Promise<Identity>;   // throws on failure
}

Security notes for the test phase: rate-limit /auth/login per IP, keep username_only mode off in production builds, and seed the admin account from an environment variable rather than a default password.

6. Data model

Products are catalogue items; an auction is one product offered inside one campaign with its own pricing/timing rules. The admin form creates both in one step, but the separation lets you re-list a product in a later campaign.

CREATE TYPE campaign_status AS ENUM ('draft','scheduled','live','finished');
CREATE TYPE auction_status  AS ENUM ('pending','live','ended','cancelled');

CREATE TABLE users (
  id            BIGSERIAL PRIMARY KEY,
  username      TEXT UNIQUE NOT NULL,               -- login name (test phase) / mapped from SSO later
  email         TEXT UNIQUE,                         -- optional now, filled by SSO later
  display_name  TEXT NOT NULL,
  password_hash TEXT,                                -- NULL in username-only test mode or for SSO users
  auth_provider TEXT NOT NULL DEFAULT 'local',       -- 'local' | 'oidc' | 'saml' …
  external_id   TEXT,                                -- subject id from the SSO provider
  locale        TEXT NOT NULL DEFAULT 'vi',          -- 'vi' | 'en'
  role          TEXT NOT NULL DEFAULT 'user',        -- 'user' | 'admin'
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (auth_provider, external_id)
);

CREATE TABLE products (
  id             BIGSERIAL PRIMARY KEY,
  name           JSONB NOT NULL,                     -- {"vi": "...", "en": "..."}  (en falls back to vi)
  description    JSONB NOT NULL DEFAULT '{}',        -- same shape
  images         JSONB NOT NULL DEFAULT '[]',        -- [{url, alt}]
  original_price NUMERIC(14,2) NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE campaigns (
  id         BIGSERIAL PRIMARY KEY,
  name       JSONB NOT NULL,                         -- {"vi": "...", "en": "..."}
  currency   CHAR(3) NOT NULL DEFAULT 'VND' CHECK (currency IN ('VND','USD')),
  status     campaign_status NOT NULL DEFAULT 'draft',
  start_at   TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE auctions (
  id               BIGSERIAL PRIMARY KEY,
  campaign_id      BIGINT NOT NULL REFERENCES campaigns(id),
  product_id       BIGINT NOT NULL REFERENCES products(id),
  sort_order       INT NOT NULL,
  status           auction_status NOT NULL DEFAULT 'pending',
  start_price      NUMERIC(14,2) NOT NULL,
  step_price       NUMERIC(14,2) NOT NULL,
  extend_window_s  INT NOT NULL DEFAULT 30,   -- a bid in the last N s triggers extension
  extend_by_s      INT NOT NULL DEFAULT 30,   -- extension length
  max_extensions   INT,                       -- NULL = unlimited
  extension_count  INT NOT NULL DEFAULT 0,
  start_at         TIMESTAMPTZ NOT NULL,
  end_at           TIMESTAMPTZ NOT NULL,      -- planned end (never changes)
  current_end_at   TIMESTAMPTZ NOT NULL,      -- effective end (moves on extension)
  current_price    NUMERIC(14,2),             -- NULL until first bid
  leading_bid_id   BIGINT,
  leading_user_id  BIGINT,
  bid_count        INT NOT NULL DEFAULT 0,
  version          INT NOT NULL DEFAULT 0,    -- +1 on every change; clients use it to drop stale events
  UNIQUE (campaign_id, sort_order)
);
CREATE INDEX auctions_live_end_idx ON auctions (current_end_at) WHERE status = 'live';
CREATE INDEX auctions_pending_start_idx ON auctions (start_at) WHERE status = 'pending';

CREATE TABLE bids (
  id         BIGSERIAL PRIMARY KEY,
  auction_id BIGINT NOT NULL REFERENCES auctions(id),
  user_id    BIGINT NOT NULL REFERENCES users(id),
  amount     NUMERIC(14,2) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (auction_id, amount)                 -- hard guarantee: no two bids at the same price
);
CREATE INDEX bids_auction_idx ON bids (auction_id, amount DESC);

CREATE TABLE auction_results (                -- materialised at auction end
  auction_id  BIGINT PRIMARY KEY REFERENCES auctions(id),
  campaign_id BIGINT NOT NULL,
  winner_id   BIGINT REFERENCES users(id),    -- NULL = no bids
  start_price NUMERIC(14,2) NOT NULL,
  final_price NUMERIC(14,2),
  price_gain  NUMERIC(14,2) GENERATED ALWAYS AS (final_price - start_price) STORED,
  ended_at    TIMESTAMPTZ NOT NULL
);
CREATE INDEX results_gain_idx ON auction_results (campaign_id, price_gain DESC);

CREATE TABLE bid_idempotency (                -- or keep this in Redis with 60 s TTL
  key        UUID PRIMARY KEY,
  user_id    BIGINT NOT NULL,
  response   JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
Money: always NUMERIC(14,2) in the DB and a decimal library (or integer minor units) in code. Never float. For VND campaigns the API additionally enforces whole-đồng amounts (amount = trunc(amount)), so the same column serves both currencies. The currency is fixed per campaign; prices are never converted.

7. Campaign & auction lifecycle

Campaign

draft → scheduled (admin sets start_at and item order) → live (first item starts, or admin clicks "Start now") → finished (last item ended).

Admin "Start now" simply sets the first item's start_at = now(); the scheduler does the rest.

Auction item

pending → live (at start_at) → ended (at current_end_at) · cancelled by admin at any time.

Two ordering modes, chosen per campaign:

  • Scheduled: each item has its own start_at/end_at; items may overlap.
  • Sequential: item k+1 starts gap seconds after item k actually ends (including extensions). The scheduler sets its start_at when the previous one ends.

Scheduler tick (runs every second in the API process)

-- 1) start items whose time has come
UPDATE auctions SET status = 'live', version = version + 1
 WHERE status = 'pending' AND start_at <= now()
RETURNING id, campaign_id;

-- 2) end items whose effective end has passed, and materialise the result
WITH ended AS (
  UPDATE auctions SET status = 'ended', version = version + 1
   WHERE status = 'live' AND current_end_at <= now()
  RETURNING *
)
INSERT INTO auction_results (auction_id, campaign_id, winner_id, start_price, final_price, ended_at)
SELECT id, campaign_id, leading_user_id, start_price, current_price, now() FROM ended
RETURNING *;
Why this is race-safe: the UPDATE … WHERE status='live' AND current_end_at <= now() waits for any in-flight bid transaction holding the row lock, then re-evaluates the WHERE clause on the fresh row (PostgreSQL READ COMMITTED semantics). If the bid just extended the end time, the item is not ended. No bid can slip in after "ended" because the bid transaction checks status = 'live' under the same lock.

Run the tick in exactly one process. With a single API instance that is automatic; with several, guard it with a Redis lock (SET scheduler:lock NX PX 1500).

8. Bid engine – the critical path

Rules

  • Auction must be live and now() < current_end_at (server time).
  • Minimum bid = start_price if no bids yet, else current_price + step_price.
  • Amount must be a multiple of step_price above the base (optional, keeps the UI's quick-bid buttons consistent).
  • The current leader cannot raise their own bid (configurable).
  • Everything happens in one transaction holding the auction row lock.

Sequence

  1. Client POST /auctions/42/bids with { amount, idempotencyKey } (cookie JWT).
  2. Guard: authenticated · rate limit (e.g. 3 bids / 2 s per user) · idempotency key not seen before.
  3. BEGIN; SELECT … FROM auctions WHERE id = 42 FOR UPDATE – all other bids for this auction now queue behind this one (a few ms each).
  4. Validate status, time and amount against the locked row.
  5. INSERT INTO bids (the unique constraint on (auction_id, amount) is a second safety net).
  6. If current_end_at − now() ≤ extend_window_s, set current_end_at = current_end_at + extend_by_s.
  7. UPDATE auctions SET current_price, leading_*, bid_count+1, current_end_at, version+1. COMMIT.
  8. After commit: broadcast auction:bid to room auction:42; emit user:outbid to room user:{previousLeaderId}; broadcast a compact campaign:tick to the main page room.
  9. Respond 201 { auction snapshot }. On validation failure respond 409 { code, minAllowed, currentPrice, version } so the UI can offer a one-click re-bid.

Reference implementation (NestJS service, raw SQL through Prisma)

export class BidsService {
  constructor(private prisma: PrismaService, private rt: RealtimeGateway) {}

  async placeBid(auctionId: number, userId: number, amount: Decimal) {
    const result = await this.prisma.$transaction(async (tx) => {
      // 1. Serialise every bid on this auction
      const [a] = await tx.$queryRaw<Auction[]>`
        SELECT *, now() AS server_now FROM auctions WHERE id = ${auctionId} FOR UPDATE`;
      if (!a) throw new NotFoundException();

      // 2. Validate against the LOCKED row and the SERVER clock
      if (a.status !== 'live' || a.server_now >= a.current_end_at)
        throw new BidRejected('AUCTION_CLOSED', a);
      if (a.leading_user_id === userId)
        throw new BidRejected('ALREADY_LEADING', a);
      const minAllowed = a.current_price === null ? a.start_price : a.current_price.plus(a.step_price);
      if (amount.lt(minAllowed))
        throw new BidRejected('BID_TOO_LOW', a, { minAllowed });

      // 3. Record the bid
      const [bid] = await tx.$queryRaw<Bid[]>`
        INSERT INTO bids (auction_id, user_id, amount)
        VALUES (${auctionId}, ${userId}, ${amount}) RETURNING *`;

      // 4. Anti-sniping
      const remainingMs = a.current_end_at.getTime() - a.server_now.getTime();
      const canExtend = a.max_extensions === null || a.extension_count < a.max_extensions;
      const extended = canExtend && remainingMs <= a.extend_window_s * 1000;
      const newEnd = extended ? new Date(a.current_end_at.getTime() + a.extend_by_s * 1000) : a.current_end_at;

      // 5. Update auction state
      const [updated] = await tx.$queryRaw<Auction[]>`
        UPDATE auctions SET
          current_price = ${amount}, leading_bid_id = ${bid.id}, leading_user_id = ${userId},
          bid_count = bid_count + 1, current_end_at = ${newEnd},
          extension_count = extension_count + ${extended ? 1 : 0}, version = version + 1
        WHERE id = ${auctionId} RETURNING *`;

      return { bid, auction: updated, previousLeaderId: a.leading_user_id, extended };
    }, { isolationLevel: 'ReadCommitted', timeout: 5000 });

    // 6. Publish only after the commit succeeded
    this.rt.broadcastBid(result);
    if (result.previousLeaderId && result.previousLeaderId !== userId)
      this.rt.notifyOutbid(result.previousLeaderId, result);
    return result;
  }
}
Same price, same millisecond: user A and user B both send 1,200,000. A acquires the row lock first, inserts, sets current_price = 1,200,000, commits. B then acquires the lock, reads the fresh row, computes minAllowed = 1,200,000 + step, and fails with BID_TOO_LOW. B's UI shows "Someone bid 1,200,000 a moment ago – bid 1,250,000?" with a one-click button. The unique index would reject the duplicate even if the application logic had a bug.

Alternative: Redis Lua script

A Lua script in Redis (atomic by design) can hold the hot auction state and validate/apply bids in ~0.1 ms, with Postgres written asynchronously. This is what you would do at thousands of bids per second. At 100 users it adds a second source of truth and a recovery path for no benefit. Stay with the Postgres row lock.

9. Anti-sniping extension

extend_window_sIf a valid bid lands when current_end_at − now ≤ window, extension triggers (e.g. 30 s). extend_by_sNew end = current_end_at + extend_by (e.g. 30 s): every qualifying bid adds N seconds. Implemented this way (2026-10-26); the alternative “ensure at least N seconds remain” (max(current_end, now + N)) grows slower and is a one-line change. max_extensionsOptional cap so an item cannot run forever (e.g. 20). NULL = unlimited.

Admin UI exposes all three per product with defaults from the campaign. The planned end_at is kept for reporting; the UI shows current_end_at and a small "+30 s extended" badge when the auction:bid event carries extended: true.

Because the extension decision is made inside the same locked transaction as the bid, there is no window where the scheduler could end the auction between "bid accepted" and "end time moved".

10. Real-time & notifications

Rooms

  • user:{userId} – joined automatically after socket auth; receives private events.
  • auction:{auctionId} – joined on the auction page; full bid stream.
  • campaign:{campaignId} – joined on the main page; compact updates (price, end time, status) for every item plus winners-board changes.

Events

EventDirectionPayload / purpose
auction:join / auction:leaveclient → server{ auctionId }. Server replies with auction:state.
auction:stateserver → clientFull snapshot: auction row, last 20 bids (bidder names masked), serverTime. Sent on join and after reconnect.
auction:bidserver → room{ auctionId, amount, bidderMasked, bidCount, currentEndAt, extended, version, serverTime }
auction:started / auction:endedserver → room + campaign{ auctionId, status, winnerMasked?, finalPrice?, version }
user:outbidserver → user room{ auctionId, productName, yourBid, newPrice, currentEndAt } → sound + browser notification.
user:wonserver → user roomAt auction end for the leader.
campaign:tickserver → campaign room{ auctionId, currentPrice, currentEndAt, status, version } for the main page cards.
time:syncserver → all (every 15 s){ serverTime } to keep countdowns honest.

Payloads carry version; the client ignores any event whose version is ≤ the version it already holds, so out-of-order delivery or a replayed snapshot cannot move the UI backwards.

Client: sound + browser notification

// Browsers block audio and Notification prompts until a user gesture.
// Unlock both on the first click of "Place bid" / "Enable alerts".
const outbidSound = new Audio('/sounds/outbid.mp3'); outbidSound.preload = 'auto';

async function enableAlerts() {
  try { await outbidSound.play(); outbidSound.pause(); outbidSound.currentTime = 0; } catch {}
  if ('Notification' in window && Notification.permission === 'default')
    await Notification.requestPermission();
}

socket.on('user:outbid', (e) => {
  outbidSound.play().catch(() => {});
  toast.warning(`You were outbid on ${e.productName}. New price ${fmt(e.newPrice)}`,
                { action: { label: 'Bid again', onClick: () => router.push(`/auctions/${e.auctionId}`) } });
  if (Notification.permission === 'granted' && document.visibilityState === 'hidden') {
    const n = new Notification(`Outbid: ${e.productName}`, {
      body: `New price ${fmt(e.newPrice)} – ends ${fmtTime(e.currentEndAt)}`,
      tag: `outbid-${e.auctionId}`,          // replaces previous alert for the same item
      icon: '/icons/auction-192.png',
    });
    n.onclick = () => { window.focus(); router.push(`/auctions/${e.auctionId}`); };
  }
});
Scope note: the Notification API only works while a tab with the site is open (even in the background). Alerts for users who closed the browser need Web Push (service worker + VAPID) and/or email, which is a clean phase-2 addition using the same user:outbid hook.

  JOIN auctions a ON a.id = r.auction_id
  JOIN products p ON p.id = a.product_id
  LEFT JOIN users u ON u.id = r.winner_id
 WHERE r.campaign_id = $1 AND r.winner_id IS NOT NULL
 ORDER BY r.price_gain DESC, r.ended_at ASC
 LIMIT 50;

Served with a 2-second HTTP cache header; the main page also receives auction:ended over the campaign room and refetches, so the board updates within a second of each close. Public views show masked names (e.g. Ng***n); admins see full names.

12. Time, scheduling & reconnection

Server-authoritative clock

Every snapshot and event includes serverTime. The client keeps offset = serverTime − Date.now() (smoothed) and renders current_end_at − (Date.now() + offset). A bid is never rejected on the client because of time; the server decides, and the client shows the 409 message if it was late.

Reconnection

  1. Socket.IO reconnects automatically with backoff.
  2. On connect, the client re-emits auction:join for the page it is on; the server replies with a fresh auction:state.
  3. The client compares version and replaces its state if the snapshot is newer.
  4. While disconnected, the UI shows a small "reconnecting…" pill and disables the bid button to avoid confusing failures.

Scheduler precision

A 1-second tick means an auction can end up to ~1 s after current_end_at; bids in that gap are still rejected by the time check inside the transaction, so fairness is unaffected. If you want exact-second UX, the tick can run at 250 ms – the queries are index-only and cost nothing.

14. Handling 50–100 concurrent users

ConcernNumbers & measures
WebSocket connections100–300 sockets (multiple tabs). A single Node process handles tens of thousands. Keep heartbeats at defaults (25 s ping).
Bid write throughputWorst case in the last 30 s of a hot item: 100 users × 1 bid/s = 100 tx/s on one row. Each tx is ~2–5 ms under lock → max ~50% lock utilisation on one item. Postgres on a small VPS does 1–3k simple tx/s.
Fan-outEach bid → 1 room broadcast (≤300 sockets) + 1 private emit. 100 bids/s × 300 = 30k small messages/s; fine for Node + uWebSockets.js engine if needed, trivial at the real expected rate (a few bids/s).
Rate limitingPer user: 3 bids per 2 s (Redis sliding window). Per IP on auth: 10 / min. Protects the lock queue from a stuck client in a loop.
IdempotencyClient generates a UUID per submit; server stores the response in Redis for 60 s; retried/double-clicked requests return the original result instead of a second bid.
Read loadMain page SSR hits GET /campaigns/current; cache 1–2 s in memory. All other state comes over the socket, so refresh storms do not touch Postgres heavily.
Connection poolPrisma pool 10–20. Bids on different items run in parallel; bids on the same item queue on the row lock, not on the pool, as long as pool ≥ expected concurrent distinct items + headroom.
Scaling out laterAdd Socket.IO Redis adapter, run 2+ API replicas, move the scheduler behind a Redis lock. No schema change required.
Load test before launchk6: 100 VUs hammering POST /bids on one item for 60 s, assert p95 < 150 ms and zero duplicate prices. artillery socket.io: 300 subscribers receiving every event, assert no drops.

15. Edge cases

CaseBehaviour
Two users, same amount, same instantRow lock serialises; first commits, second gets BID_TOO_LOW with the new minimum. Unique index as backstop.
Bid arrives 50 ms after endTransaction compares now() to current_end_at under lock → AUCTION_CLOSED, even if the scheduler has not flipped status yet.
Scheduler and bid race at the endPostgres re-evaluates the UPDATE's WHERE after the lock; an extension made by the bid prevents the close. See §7.
Double-click / retry after timeoutIdempotency key returns the first response; no duplicate bid.
User's clock is wrongIrrelevant – countdown uses server offset; validation uses server time.
Socket drops during the final secondsBid still goes through REST; on reconnect the snapshot replaces local state. Button disabled while reconnecting to avoid confusion.
Leader bids against themselvesRejected (ALREADY_LEADING) unless the campaign enables it.
Amount not aligned to stepServer rounds down to the nearest valid step or rejects with BID_INVALID_STEP (pick one; rounding is friendlier).
Admin cancels a live itemCancel takes the row lock, sets cancelled, broadcasts auction:ended { cancelled: true }; no result row.
Admin edits price/time of a live itemBlocked in the UI and API; only pending items are editable (except cancel / extend-by-admin).
No bids by end timeResult row with winner_id = NULL; excluded from the winners board; shown as "no winner".
Process restart mid-auctionAll state is in Postgres; on boot the scheduler tick resumes; clients reconnect and resync. Nothing is lost.
